# کاندیدای یکپارچهٔ اصلاح Native — انتشار همچنان BLOCKED

درخواست مالک: آزمون نهایی و سپس APK برای تست؛ نه تحویل زودهنگام APK.

این شاخه، گام ادغام را انجام می‌دهد؛ خروجی پژوهشی Xray فقط پس از تطبیق دقیق با AAR بازتولیدپذیر، سورس، گراف کامل JNI، ABI و Java API ثبت‌شده در شواهد عمومی وارد workspace کاندیدا می‌شود. مسیر upstream/production پیش‌فرض، signer generation3 و انتشار stable تغییر نمی‌کنند.

## قرارداد

- `xray-candidate-lock.json` هش AAR، هر دو JNI، سورس واقعی و generated go.mod را pin می‌کند. عدم تطبیق، build را متوقف می‌کند؛ fallback به AAR قبلی در حالت کاندیدا نداریم.
- `xray_candidate.py build` همان سازندهٔ بررسی‌شده را اجرا می‌کند، خروجی و سورس را بررسی می‌کند و AAR را فقط در workspace کاندیدا جایگزین می‌کند.
- `source_bundle.py --candidate-xray` سورس patchشدهٔ بررسی‌شده را بسته‌بندی می‌کند؛ `vendor()` پایه را دوباره اجرا نمی‌کند. manifest/provenance همراه سورس است.
- SCA با `--native --candidate-xray` شش باینری واقعی را بررسی می‌کند و برای JNI فقط شواهد کاملِ متصل به بایت‌های AAR را می‌پذیرد. `--candidate-xray` بدون `--native` مجاز نیست. گراف‌های source به‌صورت readonly خوانده می‌شوند.
- AGP نباید JNI بررسی‌شده را strip کند؛ تطبیق هش همهٔ باینری‌های داخل هر سه APK الزامی است. نبود APK نباید به موفقیت تهی تبدیل شود.
- build این مرحله unsigned و secret-free است. artifact داخلی برای اعتبارسنجی نگه‌داری می‌شود، **نه برای تحویل یا نصب کاربر**. workflow حق sign، tag یا انتشار ندارد.

## آزمون‌ها و معیار پایان

۱. آزمون قراردادها، منفی‌ها و source-reset؛ host/protocol واقعی.
۲. ساخت چهار CLI Android و دو JNI بازسازی‌شده؛ تست Java/Android و lint.
۳. source bundle متناظر، SCA کامل و بررسی بایت‌های APK.
۴. سپس نصب/ارتقا/backup/updater روی ARM معتبر و امضای همان generation3 در مرحلهٔ مجزا؛ تنها بعد از تکمیل gateها تحویل APK ممکن است.

آزمایش محیط ARM این بار kernel log و وضعیت ناقص ADB را با مهلت محدود ثبت می‌کند؛ نتیجهٔ شکست بوت به APK نسبت داده نمی‌شود و timeout/SELinux/TLS برای اعلام موفقیت تغییر نمی‌کند. مهلت تشخیصی کوتاه‌تر، gate نصب یا ادعای عدم امکان بوت نیست.
