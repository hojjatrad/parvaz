# پرواز — نتیجهٔ مرحلهٔ دوم: ورود چندقالبی و اشتراک پایدار

**تاریخ:** ۸ سپتامبر ۲۰۲۶

**هدف:** استفاده از خروجی پنل‌های مختلف روی اندروید ۱۰ به بالا

**شاخهٔ محلی:** `fix/panel-import-and-stable-refresh`

**مبنای این مرحله:** پایان مرحلهٔ A، کامیت `6cf5f9f`

> این مرحله در سورس و تست‌های JVM انجام شده است. هنوز APK تازه ساخته نشده، تست گوشی/هستهٔ Xray و ساخت کامل Gradle انجام نشده و هیچ تغییر این مرحله به GitHub push نشده است. اعداد تست زیر تأیید اتصال واقعی یا سازگاری همهٔ پنل‌ها نیستند.

## ۱. پردازش واقعی YAML به‌جای شکستن متن بر اساس خط

parser دست‌نویس Clash با **SnakeYAML 2.4 و SafeConstructor** جایگزین شد. اکنون نگاشت inline، فهرست‌ها، تنظیمات تو‌در‌تو، متن فارسی و کوتیشن‌ها پردازش می‌شوند.

حفاظت‌های ورودی:

- غیرفعال‌بودن ساخت اشیای دلخواه Java از YAML.
- ردکردن کلید تکراری، alias، چند سند در یک ورودی و ساختار ناقص.
- سقف طول ورودی، عمق ۳۲ و تعداد رخدادهای YAML؛ محدودیت عمومی ۵۰۰۰ پروفایل هم برقرار است. یک سند بسیار پیچیده ممکن است پیش از رسیدن به ۵۰۰۰ پروفایل به سقف ساختاری برسد.
- حفظ scalarهای ساده به‌صورت رشته؛ رمز `yes` به boolean تبدیل نمی‌شود و short-id مانند `00123456` صفرهای ابتدایی‌اش را از دست نمی‌دهد.
- خطاها کد و شماره دارند؛ رمز، UUID واقعی و URL محرمانه در گزارش جدید پردازش چاپ نمی‌شوند. این ادعا به معنی ممیزی تمام لاگ‌های قدیمی برنامه نیست.
- متن JSON باید کامل مصرف شود؛ دادهٔ اضافی پس از JSON یا دو JSON چسبیده به هم به‌عنوان یک پاسخ سالم پذیرفته نمی‌شوند.

## ۲. وضعیت قالب‌ها و نگاشت تنظیمات

| ورودی/تنظیم | کار انجام‌شده | محدودیت |
|---|---|---|
| Clash/Mihomo YAML | بلوک، inline، فهرست تو‌در‌تو و قالب JSON دارای `proxies` | اجرای خود Clash نیست |
| VLESS/VMess/Trojan/SS | نگاشت فیلدهای اصلی، TLS، SNI و اعتبارسنجی اولیهٔ فیلدهای لازم | صحت همهٔ مقادیر باید با هسته هم آزمایش شود |
| Reality | کلید عمومی و short-id از ساختارهای nested | گواهی/کلید و سرور واقعی در این محیط آزموده نشده‌اند |
| WS و gRPC | مسیر، Host و نام سرویس | headerهای دلخواه و early-data کامل پشتیبانی نشده‌اند |
| ALPN/uTLS | فهرست ALPN؛ fingerprintهای نگاشت‌شده با توجه به فرمت | پین گواهی با fingerprint مرورگر اشتباه گرفته نمی‌شود؛ pin پشتیبانی‌نشده رد می‌شود |
| SOCKS و HTTP در Sing-box/Clash | نام کاربری، رمز و نوع قابل‌تبدیل | هنوز Import Router برای تشخیص هر لینک مستقیم HTTP proxy ساخته نشده است |
| WireGuard در Clash | کلیدها، آدرس داخلی IPv4/IPv6، reserved و MTU | کلیدهای نمونه ساختگی‌اند؛ بررسی رمزنگاری و اتصال واقعی انجام نشده |
| WireGuard در Sing-box | خروجی قدیمی و endpoint جدید با یک peer | multi-peer، system endpoint و گزینه‌های خارج از مدل رد می‌شوند |
| endpoint با IPv6 | قرارگرفتن IPv6 در براکت هنگام ساخت endpoint وایرگارد | فقط صحت رشتهٔ خروجی تست شده است |
| پاسخ API پنل دارای `links` | تبدیل آرایهٔ لینک‌ها؛ metadata تنها دیگر سرور جعلی نمی‌سازد | adapter عمومی برای هر پاسخ دلخواه API پنل نیست |
| Hysteria2/TUIC | حفظ فیلدهای نگاشت‌شده و هشدار قابلیت هسته | **هنوز با هستهٔ فعلی قابل اتصال نیستند** |

**سیاست مهم:** گزینهٔ اتصالِ ناشناخته یا غیرقابل‌تبدیل، گره را با خطای مشخص رد می‌کند؛ به‌جای آنکه بی‌صدا حذف شود و یک کانفیگ ظاهراً سالم اما متفاوت ساخته شود. مثلاً plugin مربوط به Shadowsocks، detour، پین گواهی یا گزینهٔ early-data خارج از مدل، فعلاً نیازمند توسعهٔ جداگانه‌اند.

این سیاست عمداً محافظه‌کارانه است: ممکن است بعضی خروجی‌های پنل که قبلاً ناقص وارد می‌شدند اکنون صریحاً رد شوند. هدف «واردشدن ظاهری به هر قیمت» نیست.

**قواعد routing، DNS، گروه‌ها و providerهای Clash/Sing-box اجرا یا کامل منتقل نمی‌شوند.** مسیر فعلی استخراج سرور است و این محدودیت هشدار دارد. JSON خام Xray نیز همچنان مسیر استخراج یک outbound دارد، نه اجرای تمام فایل. بنابراین هنوز ادعای پشتیبانی کامل از هر کانفیگ/پنل درست نیست.

## ۳. گزارش ورود کانفیگ

نتیجهٔ پردازش اکنون شامل این موارد است:

- پروفایل‌های شناخته‌شده؛ تعداد ردشده و هشدارها.
- کدهای خطا/هشدار با شمارهٔ ورودی در بخش مربوط.
- وضعیت خطای کلی و اینکه آیا نتیجه برای جایگزینی خودکار امن است.

در ورود دستی، پروفایل‌های پذیرفته‌شده وارد می‌شوند و برای ردشدن‌ها/هشدارها گزارش نمایش داده می‌شود. کدهای فنی فعلاً انگلیسی‌اند؛ عنوان و خلاصهٔ شمارشی فارسی/انگلیسی دارد. تغییرات رابط از نظر سورس و XML بررسی شده‌اند اما روی دستگاه یا Android UI test اجرا نشده‌اند.

وجود پروفایل شناخته‌شده به معنی قابل‌اتصال‌بودن آن با هسته نیست؛ مثلاً Hysteria2/TUIC هشدار `CORE_UNSUPPORTED` می‌گیرند. خاموش‌کردن بررسی TLS در یک کانفیگ واردشده نیز هشدار جداگانه دارد؛ این با امنیت دریافت HTTPS اشتراک، که در مرحلهٔ A اصلاح شد، متفاوت است.

## ۴. به‌روزرسانی بدون حذف اولیهٔ همهٔ سرورها

روش قبلی «حذف پروفایل‌ها → ذخیره → افزودن دوباره → ذخیره» از مسیر refresh حذف شد.

روش جدید:

۱. پیش از دانلود از metadata اشتراک و شمارهٔ تغییرات store یک snapshot گرفته می‌شود.
۲. پاسخ کامل دریافت و پردازش می‌شود.
۳. اگر نتیجه خالی، خراب یا حتی بخشی از آن ردشده باشد، **فهرست سالم قبلی جایگزین نمی‌شود**.
۴. برای پاسخ قابل‌قبول، برنامهٔ جایگزینی در حافظه تهیه می‌شود.
۵. profiles، metadata اشتراک و پینگ‌ها با **یک Editor در SharedPreferences** نوشته می‌شوند؛ سپس فهرست‌های حافظه زیر همان قفل به‌روز می‌شوند.

### چه چیزهایی حفظ می‌شوند؟

- سرور با پارامترهای اتصال یکسان، ID قبلی و پینگ قبلی را حفظ می‌کند؛ تغییر صرف نام نمایشی یا نمایش لینک ID تازه ایجاد نمی‌کند.
- چون ID ثابت می‌ماند، اشاره‌گر سرور انتخاب‌شده و علاقه‌مندی‌های مربوط به همان ID باقی می‌مانند؛ این تنظیمات در refresh بازنویسی نمی‌شوند.
- سرور مشترک بین دو اشتراک با مالکیت مستقل نگهداری می‌شود؛ refresh یکی آن را از دیگری حذف نمی‌کند.
- تشخیص تکراری‌ها به SNI، کلید Reality، short-id، flow، رمز دوم، cipher و سایر فیلدهای ذخیره‌شدهٔ اتصال هم حساس است.
- در صورت وجود تکراری‌های قدیمی با چند ID، در تطبیق همان اتصال، ID انتخاب‌شده اولویت دارد.
- سهمیه، زمان refresh و تعداد یکتای پروفایل‌های اشتراک همراه همان snapshot به‌روز می‌شوند؛ نبود هدر سهمیه اطلاعات قبلی را بی‌دلیل صفر نمی‌کند.

### مرزهای این حفاظت

- اگر سرور واقعاً از پنل حذف شود، قابل حفظ به‌عنوان سرور فعالِ همان اشتراک نیست. اگر اطلاعات اتصال تغییر کند، ID تازه می‌گیرد و آمار قدیمی به اتصال متفاوت منتقل نمی‌شود. حفظ انتخاب تضمین‌شده برای سرور **هم‌ارز و همچنان موجود** است، نه هر تغییر دلخواه پنل.
- اصلاح نگاشت‌های ناقص قدیمی نیز ممکن است fingerprint اتصال را تغییر دهد؛ حفظ تمام IDهای ساخته‌شده از کانفیگ اشتباه قبلی تضمین نمی‌شود.
- پاسخ واقعاً خالی هم فعلاً اجازهٔ حذف خودکار نمی‌دهد؛ حذف عمدی باید جداگانه انجام شود.
- نوشتن `SharedPreferences.apply()` غیرهم‌زمان است. این کار حذفِ میانی را از بین می‌برد، اما **تضمین نوشتن قطعی روی دیسک در لحظهٔ قطع برق نیست**. مهاجرت Room، آزمون crash واقعی و اصلاح تمام مسیرهای backup/restore هنوز انجام نشده‌اند.
- تست خطای نوشتن از Editor آزمایشی استفاده می‌کند؛ این را نباید با آزمون شکست واقعی دیسک Android یکی دانست.

## ۵. هم‌زمانی و Worker

- refresh دستی و دوره‌ای از یک موتور مشترک استفاده می‌کنند؛ درخواست هم‌زمان دوم، وضعیت «در حال اجرا» و قابل retry می‌گیرد، نه دانلود موازی و جایگزینی رقیب.
- اگر store هنگام دانلود تغییر کند، پاسخ قدیمی رد می‌شود. غیرفعال‌شدن، حذف یا تغییر URL اشتراک نیز بررسی می‌شود.
- موفقیت یک اشتراک خطای اشتراک دیگر را پنهان نمی‌کند؛ خلاصه تعداد موفق، ناموفق، پروفایل و هشدار را نشان می‌دهد.
- Worker دیگر thread رهاشده و انتظار latch ندارد؛ نتیجهٔ واقعی موتور را به WorkManager برمی‌گرداند.
- timeout، خطای شبکه، HTTP 408/429 و خطاهای سمت سرور قابل retry هستند. URL نامعتبر، TLS نامعتبر و پاسخ غیرقابل‌پردازش retry فوری نمی‌گیرند؛ اجرای دوره‌ای بعدی جدا از retry همان اجراست.
- توقف کار به‌شکل مشارکتی بین مراحل و پیش از ثبت پاسخ بررسی می‌شود. درخواست شبکهٔ درحال‌خواندن الزاماً همان لحظه قطع نمی‌شود و ممکن است تا timeout ادامه یابد. این بخش روی lifecycle واقعی Android/WorkManager هنوز تست نشده است.

## ۶. تست‌های اجراشده

فرمان:

```bash
bash tools/audit/run.sh
```

نتایج ثبت‌شده در `docs/audit/phase-b-results.txt`:

| مجموعه | تعداد assertion موفق |
|---|---:|
| رگرسیون مرحلهٔ A: parser/builder | ۳۵ |
| HTTP و TLS | ۶۳ |
| مرحلهٔ B: YAML، Sing-box، identity، store، refresh و Worker | ۹۳ |
| **جمع** | **۱۹۱** |

تست‌های جدید شامل ورودی nested/inline، alias و tag ناامن، گزینهٔ نامعتبر، حفظ صفرهای short-id، WireGuard قدیم/جدید، حذف‌نشدن فهرست در پاسخ ناقص، حفظ ID و پینگ، مالکیت مستقل اشتراک، stale response، درخواست هم‌زمان، توقف و retry واقعی منطق Worker هستند.

بخشی از تست HTTP/TLS روی سرور واقعی loopback در همین محیط اجرا شد. هیچ لینک خصوصی کاربر یا پنل زنده‌ای تماس داده نشد. fixtureها در `app/src/test/resources/import/` **ساختگی و بدون اطلاعات فعال** هستند؛ این‌ها تأیید سازگاری نسخه‌های مشخص مرزبان، هیدیفای، 3x-ui و دیگر پنل‌ها نیستند.

### محدودیت تست‌ها

کلاس‌های parser، مدل، builder، ProfileStore، موتور refresh و Worker واقعاً کامپایل/اجرا شدند؛ اما APIهای Android مانند Context، SharedPreferences، Handler و WorkManager جایگزین آزمایشی دارند. تست‌های URI اندرویدی، زمان‌بندی واقعی WorkManager، رابط، دیسک واقعی، native Xray و کل برنامه در محیط Android انجام نشده‌اند. هشدارهای unchecked مربوط به کدهای generic قدیمی/ابزار تست نیز هنوز وجود دارند.

## ۷. گیت‌هاب، CI و فضا

- workflow سبک `Subscription regression tests` اضافه شد تا پس از push، همین تست‌های JVM روی GitHub Actions اجرا شوند. مجوز آن فقط `contents: read` است و secret انتشار نمی‌خواهد.
- گزارش تست CI فقط سه روز نگهداری می‌شود. workflow فعلاً **در GitHub اجرا نشده** و ساخت APK هم انجام نمی‌دهد.
- نسخهٔ SnakeYAML pin شده، هش JAR در ابزار تست کنترل می‌شود و متن مجوز Apache 2.0 همراه assets قرار گرفته است. جزئیات در `docs/THIRD-PARTY.md` آمده؛ کل dependency graph قدیمی هنوز ممیزی کامل نشده است.
- تغییرات روی شاخهٔ محلی نگهداری شده و patch برای انتقال آماده می‌شود. دسترسی نوشتن GitHub هنوز وجود ندارد؛ push یا Pull Request ساخته نشده است.
- فضای کار در ابتدا و انتها بررسی شد؛ حدود ۱۹٫۷ GiB آزاد است. فایل‌های نصبی قدیمی دانلود نشده‌اند. دادهٔ کامپایل و گواهی آزمایشی داخل cache نادیده‌گرفته‌شده است؛ سورس یا اطلاعات بدون پشتیبان حذف نشده‌اند.

## مرحلهٔ بعد پیشنهادی

**ساخت کامل Android و تست نصب/اتصال روی Android 10 و نسخه‌های جدیدتر**، پیش از انتشار نسخهٔ نصبی. در کنار آن، تکمیل Import Router برای Share و فایل، سپس رفع ایرادهای مستقل هات‌اسپات و تست نشت. Hysteria2/TUIC نیز برای اتصال واقعی همچنان نیازمند تصمیم دربارهٔ هستهٔ دوم هستند.
