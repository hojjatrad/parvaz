# انتظار پس از شروع اتصال — بررسی شبکهٔ پیش‌فرض

**وضعیت: اصلاح در شاخهٔ آزمایشی؛ نسخهٔ پایدار همچنان 1.26.3 است.** کاربر گزارش کرده که تغییر آمار/warmup نسخهٔ 1.26.3 انتظار تا آماده‌شدن سرور را برطرف نکرده است. بنابراین کاهش زمان اتصال روی گوشی، تأییدشده محسوب نمی‌شود.

## ایراد بازتولیدشده

NetworkMonitor پیش‌تر برای تمام شبکه‌های دارای INTERNET callback می‌گرفت، نه فقط شبکهٔ پیش‌فرض برنامه. onAvailable هر شبکهٔ دوم، و حتی تغییر capabilities یک شبکهٔ فرعی، می‌توانست جای شبکهٔ فعلی را بگیرد و reconnect را زمان‌بندی کند. runnable reconnect در صورت فعال‌بودن سرویس، هسته را متوقف و دوباره راه‌اندازی می‌کند. در نتیجه روشن‌شدن/اعلان شبکهٔ همراه کنار وای‌فای می‌تواند یک راه‌اندازی اضافی ایجاد کند. این علتِ ممکنِ تأخیر است، نه اثبات علت روی گوشی کاربر.

- آزمون اولیه `f164792` در 34448273275 به علت استفادهٔ fixture از متد hidden در android.jar کامپایل نشد؛ آن شکست، بازتولید رفتار نبود.
- fixture در `9412d13` با ShadowNetworkCapabilities اصلاح شد، بدون حذف assertionها.
- [34448496242](https://github.com/hojjatrad/parvaz/actions/runs/34448496242): **205 اجرا، 6 شکست، صفر error/skip**. سه سناریوی شبکهٔ فرعی/اعلان capability/ callback پس از توقف در هر دو SDK 29/34 شکست خوردند. سایر آزمون‌ها عبور کردند. شواهد: [network-startup-baseline.json](network-startup-baseline.json).

## اصلاح 533510d

- ثبت default-network callback به جای درخواست همهٔ شبکه‌های INTERNET.
- پذیرش رخداد فقط برای شبکهٔ پیش‌فرض فعلیِ برنامه، دارای قابلیت اینترنت و غیر-VPN. onCapabilitiesChanged از capabilities دریافتی استفاده می‌کند؛ اگر داده در onAvailable هنوز موجود نباشد، همان مرحله شبکه را آماده فرض نمی‌کند.
- تغییر نوع حمل یک شبکهٔ فرعی دیگر باعث reconnect نمی‌شود.
- نادیده‌گرفتن callback متعلق به ثبت قدیمی یا ناظر متوقف‌شده؛ بررسی دوبارهٔ شبکهٔ فعلی پیش از اجرای reconnect با تأخیر.
- رخداد VPN به‌تنهایی به‌عنوان قطع شبکهٔ فیزیکی تفسیر نمی‌شود.
- debounce فعلی 1200 ms برای تغییر واقعی شبکه حفظ شده است؛ انتظار 300 ms داخل مسیر reconnect در این اصلاح دست‌کاری نشده است.

## آزمون اصلاح

NetworkMonitorRegressionTest هشت سناریو روی SDK 29/34 دارد: شبکهٔ فرعی، capability فرعی، callback پس از توقف، تغییر واقعی شبکهٔ پیش‌فرض، تکرار اعلان همان شبکه، VPN overlay، قطع/بازگشت واقعی و callback ثبت قبلی پس از start دوباره.

این آزمون‌ها callbackهای شبیه‌سازی‌شدهٔ Robolectric و زمان‌بندی reconnect را بررسی می‌کنند؛ اندازه‌گیری اتصال واقعی گوشی، اجرای خود هسته در هر سناریو یا کنترل تمام reconnectهای از قبل در حال اجرا نیستند. host regressionهای قبلی با 53 assertion refresh/dedup نیز عبور کردند.

## چیزهایی که این اصلاح ادعا نمی‌کند

- نتیجهٔ API شروع هسته هنوز به‌تنهایی اثبات handshake با سرور نیست. این تغییر، جابه‌جاکردن برچسب «متصل» یا تولید ترافیک/سرعت ساختگی نیست.
- حذف یک restart غیرضروری، تضمین صفرشدن زمان DNS، handshake یا اولین درخواست تمام پروتکل‌ها نیست. اتصال‌های مبتنی بر TCP بدون multiplexing الزاماً یک ارتباط سرور مشترک را برای تمام برنامه‌ها نگه نمی‌دارند.
- تأخیر tap-to-usable-traffic و علت دقیق روی گوشی کاربر هنوز اندازه‌گیری نشده است. اگر علت از مسیر دیگری باشد، این اصلاح به‌تنهایی آن را حل نمی‌کند.
- تا تأیید آزمون اصلاح، ساخت امضاشده و gateهای انتشار، APK یا نسخهٔ جدید آماده اعلام نمی‌شود؛ v1.26.3 و فایل‌های آن تغییر نمی‌کنند.
