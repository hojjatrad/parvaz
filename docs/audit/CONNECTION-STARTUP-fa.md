# شروع ارتباط و نمایش سریع‌تر آمار — 1.26.3

درخواست کاربر: فاصلهٔ لمس اتصال تا شروع ارتباط و نمایش آپلود/دانلود روی بیشتر کانفیگ‌ها طولانی است. کاربر هنوز مشخص نکرده که اینترنت قبل از حرکت نمودار قابل استفاده است یا نه؛ بنابراین هر دو مسیر بررسی می‌شوند. هیچ کاهش زمان روی گوشی واقعی هنوز اندازه‌گیری نشده است.

## یافته‌های کد

- آغاز ticker آمار در اتصال اولیه، اتصال مجدد و تعویض سرور یک ثانیه تأخیر ثابت داشت.
- موفقیت startLoop/getIsRunning نشان‌دهندهٔ راه‌اندازی هستهٔ محلی است؛ برقراری اولین ارتباط خارجی را اثبات نمی‌کند. بسیاری از outboundها هنگام اولین درخواست ارتباطشان را شروع می‌کنند.
- نخستین health probe با فاصلهٔ تنظیم‌شده (پیش‌فرض 15 ثانیه) اجرا می‌شود و با خاموش‌بودن auto-switch اصلاً اجرا نمی‌شود؛ آن را نباید شرط شروع اینترنت دانست.

## تغییر 1.26.3

1. اولین نمونهٔ آمار پس از 250 میلی‌ثانیه زمان‌بندی می‌شود؛ سه ثانیهٔ اول نمونه‌برداری 250 میلی‌ثانیه‌ای است و بعد به یک ثانیه برمی‌گردد. شلوغی scheduler/UI می‌تواند اجرای واقعی را دیرتر کند؛ این عدد، زمان تضمینی اتصال گوشی نیست.
2. سرعت از دلتا و زمان واقعی monotonic محاسبه می‌شود. بایت‌های واقعیِ مصرف، session و دفتر روزانه همان دلتاها هستند؛ چهار برابرشدن دفعات نمونه‌برداری نباید سرعت را یک‌چهارم یا مصرف را چهار برابر کند.
3. اعلان و بازسازی سهمیه حداکثر یک بار در ثانیه انجام می‌شوند. flush دفتر روزانه بر اساس 30 ثانیهٔ واقعی است، نه تعداد tick؛ نمونهٔ صفر نوشتن بیهودهٔ شمارنده‌ها ایجاد نمی‌کند.
4. هسته پس از راه‌اندازی، یک HEAD کوچک و غیرمسدودکننده به ping_url فعلی می‌فرستد؛ فقط URL سالم HTTPS و بدون userinfo/fragment پذیرفته می‌شود. پیش‌فرض همان endpoint بررسی اتصال فعلی برنامه است، نه دانلود تست سرعت.
5. مسیر درخواست صریحاً پراکسی HTTP محلی تونل است؛ fallback سیستم/مستقیم، تغییر اعتماد TLS، دنبال‌کردن redirect و خواندن بدنه وجود ندارد. قواعد مسیریابی خود کانفیگ همچنان اعمال می‌شوند؛ اگر کاربر endpoint بررسی را direct کرده باشد، این پروب اثبات outbound پروکسی سرور نیست.
6. درخواست، timeout اتصال 1200 ms، خواندن 1800 ms و watchdog چهارثانیه‌ای دارد؛ توقف هسته آن را لغو/قطع می‌کند. فقط یک worker و بدون صف انباشته به کار می‌رود؛ در reconnect خیلی سریع، warmup جدید ممکن است به‌جای انتظار یا انباشت صرف‌نظر شود. این کار هیچ انتظار اضافی به start هسته اضافه نمی‌کند و شکست probe موجب قطع تونل، تغییر سرور یا گزارش خودکار نمی‌شود.
7. خروجی موفق probe فقط لاگ زمان بدون URL/اطلاعات اتصال است؛ زمان یا سرعت ساختگی به UI تزریق نمی‌شود. اگر ترافیک واقعی نباشد، سرعت صفر و نمودار تخت طبیعی است. بایت‌های همین درخواست واقعی در آمار محلی محاسبه می‌شوند.

## آزمون تا این مرحله

- دوازده آزمون محلی Java موفق: نرخ 250 ms، تأخیر scheduler، برگشت cadence، محدودیت اعلان، صفر/overflow؛ HEAD و timeout و نبود بدنه/redirect؛ start غیرمسدودکننده؛ لغو و watchdog؛ عدم انباشت در reconnect؛ رد URL نامناسب؛ انتخاب صریح Proxy و حفظ TLS پیش‌فرض.
- در JDK، usingProxy روی اتصال HTTPS هنوز متصل‌نشده ممکن است false برگرداند؛ آزمون مسیر به‌جای تکیه بر این نشانگر، آرگومان واقعی URL.openConnection(Proxy) را می‌سنجد و فراخوانی مسیر مستقیم را شکست می‌دهد.
- آزمون‌های host قبلی نیز موفق‌اند؛ refresh/dedup دارای 53 assertion سبز است. این تست‌ها از fixture استفاده می‌کنند و اثبات ارتباط روی گوشی/پنل واقعی نیستند.
- کامپایل Android، واحدهای کامل، R8، lint و امضای دائمی همین تغییر اکنون تأیید شده‌اند؛ شواهد پایین آمده‌اند. انتشار عمومی مرحلهٔ بعد است. نامزد بکاپ قبلی با کد متفاوت، تأیید خودکار این تغییرات نیست.

## محدودیت مهم

warmup می‌تواند اولین dial و کش DNS/اتصالِ قابل استفادهٔ مجدد را زودتر فعال کند، اما reuse به پروتکل و تنظیمات بستگی دارد. همهٔ اتصال‌های TCP/TLS بعدی الزاماً همان اتصال را استفاده نمی‌کنند. RTT سرور، ازدحام، DNS و handshake قابل حذف یا صفرکردن نیستند. این کار Kill Switch، تضمین قطع فوری تمام I/O سیستم یا تأیید زمان واقعی tap-to-internet نیست؛ نسخهٔ پایدار تا پایان gateها تغییر نمی‌کند.
